# Presentations

A deck is an argument with a spine. Build the argument before you build slides.

## Before building

1. Name the decision the deck serves and the audience that makes it. Ask only when it is not inferable from the request.
2. Collect the member's material: files in the workspace, `/downloads`, their documents, notes, and data. Use their numbers, not yours.
3. Write the outline and get it approved before creating a single slide.
4. Confirm the output format and where the file should land: a slide tool for a shared deck, or a file in `/downloads`.

## Outline rules

- One idea per slide.
- A slide title is a claim, not a topic label. "Churn doubled in Q3", not "Churn".
- Three to seven top-level sections; each section holds one to four slides.
- Every slide has a job: context, evidence, decision, or next step. If it has none, cut it.
- Open with the decision or the situation, not with an agenda slide.
- Cut thank-you and questions slides from the main flow.

## Slide content

- Put the evidence on the slide: the number, the source, and the date.
- At most about six bullets, at most about twelve words each. No paragraphs.
- One message per chart. Label axes, units, and the source.
- Speaker notes carry the detail you would say out loud; the slide carries what the audience must read.
- Cite external claims in small text on the slide that makes them.
- Use the member's own template and colours when they exist. Do not restyle their brand.

## Building

- Read the family help page before the first call: `tools help google-slides.all` for a Google deck, or the workspace tools for a file deliverable.
- Reuse the member's existing deck when they point at one; match its section rhythm.
- Placeholder text never ships: no "Lorem", no "TBD", no empty bullet. Leave the slide out instead and list it as a gap.
- Keep the working file in `/downloads` with a name the member recognises.

## Handoff

Report: the file or link, the outline in one line per section, the slide count, what needs the member's input, and the source list. State your assumptions — verbal numbers, computed dates, inferred framing — as revocable defaults they can correct in one message.
